# CLAUDE.md

Self-programming mobile app — пользователь выбирает навык, получает задания с нарастающим дискомфортом, рефлексирует после каждого. Цель — поведенческое изменение через действие, не контент.

Платформа: нативное Android-приложение для **RuStore (приоритет) и Google Play**. iOS отложен. Веб используется только для дев-просмотра.

## Стек

- **React Native + Expo SDK 54** (TypeScript, новая архитектура / Fabric)
- **Reanimated 4** + `react-native-worklets` (плагин в `babel.config.js` обязателен)
- **React Navigation v7**: Native Stack + Bottom Tabs
- **Storage**: AsyncStorage (Supabase запланирован на lazy-registration после первого «Выполнено»)
- **Шрифты**: Fraunces (display) + JetBrains Mono (моно) через `@expo-google-fonts/*`
- **Иконки**: `lucide-react-native`
- **Хаптика**: `expo-haptics`

Версии в `package.json` управляются `expo install` — не правь их руками; нужный набор подбирается под текущий SDK.

## Запуск

```bash
npm run web          # быстрый просмотр в браузере (анимации/нативка не 1:1)
npm run android      # Android Emulator (требует Android Studio + AVD)
npm start            # QR для Expo Go на физическом телефоне
```

После правки `babel.config.js` или установки нативного модуля — запуск с `--clear`.

## Структура навигации

```
RootStack
├── Onboarding              (без табов, первый запуск)
├── Main                    (Tab Navigator)
│   ├── Dashboard           (главный — карточка задания дня)
│   └── Profile             (журнал + смена навыка)
├── TaskDetail              (поверх табов, есть кнопка "назад")
└── Reflection              (поверх табов, есть "назад" с подтверждением)
```

Из табов в root-стэк сбрасываются через `navigation.getParent()?.reset(...)`. Просто `navigation.reset` сбросит только табы.

## Доменная модель

**Навык** (3 шт.): Общительность, Фокус, Дисциплина. У каждого — 5 уровней нарастающего психологического дискомфорта.

**Задание** (Task): принадлежит навыку и уровню, имеет `variantOrder` 1-5. ID формата `<prefix>-<level>-<variant>`: `soc-1-1`, `foc-3-2`, `dis-5-4`. **Не парси ID для логики** — используй `getTaskById`/`getTasksByLevel`.

**Аватар** (Avatar): идентичность — `{ name, activeSkillId, createdAt }`. Один на пользователя, постоянный. Может переключаться между навыками без потери прогресса.

**Прогресс навыка** (SkillProgress): отдельная запись для каждого навыка — `{ currentLevel, levelProgress, deferralsUsed, deferredUntil, startedAt }`. Хранится как `Record<SkillId, SkillProgress>` в `mindprog:progress`. При активации нового навыка создаётся пустой прогресс через `getOrCreateProgress`. При возврате к старому навыку — продолжение с того же уровня.

**Стрик** — не хранится, считается на лету через `computeStreak(skillId, completions)` из журнала.

**Рефлексия → Completion**: создаётся в `ReflectionScreen.save()`, добавляется в журнал. После этого `applyCompletion(skillId, progress, completions)` возвращает новый `SkillProgress`, который сохраняется через `updateProgress`.

**Смена навыка**: через `setActiveSkill(skillId)` — меняет `avatar.activeSkillId`, прогресс прошлого навыка остаётся в записи. Доступна через тап по неактивной ветке в Профиле. **Полный сброс** — отдельная кнопка «Удалить аватара» внизу профиля, вызывает `clearAll()`.

**Миграция**: `loadAvatar` детектит старый формат (где `skillId` лежал прямо в Avatar) и автоматически конвертирует в новую структуру. Это работает один раз на пользователя.

## Правила прогрессии (`src/data/progression.ts`)

Уровень растёт когда выполнено N заданий уровня **И** средний дискомфорт ≥ D:

| Переход | N | средний дискомфорт |
|---------|---|---------------------|
| 1 → 2   | 3 | ≥ 3 |
| 2 → 3   | 4 | ≥ 4 |
| 3 → 4   | 4 | ≥ 5 |
| 4 → 5   | 4 | ≥ 5 |
| 5 → финиш | 4 | ≥ 5 |

Защита от профанации: если средний дискомфорт ниже порога — система держит на уровне, давая тот же пул вариантов. Не наказание, фильтр на достоверность.

**Подача задания дня:**
- Если сегодня уже выполнено или перенесено (`deferredUntil` сегодня) → `null`.
- Если на текущем уровне 0 выполнений → всегда `variantOrder: 1` (нормальный onboarding уровня).
- Иначе — случайный из ещё не выполненных вариантов уровня.

**Стрик**: календарный день с выполненным заданием = +1. Пропуск без переноса → 0, но уровень и выполненные задания сохраняются.

**Перенос**: лимит 2 за весь путь, пишется в `avatar.deferredUntil` (иначе можно было обойти через перезапуск приложения).

## Дизайн-конвенции

- **Тёмная тема, никаких градиентов** (особенно фиолетовых). Один акцент — янтарь `#C8923A`.
- **Анимации**: появление через `FadeIn`/`FadeInDown` из Reanimated. Без bouncy spring. Длительности 300-700ms.
- **Типографика**: Fraunces для заголовков и абзацев, JetBrains Mono для меток, цифр статистики, монокнопок (`label` variant — uppercase + letter-spacing).
- **Скруглений почти нет** (`borderRadius: 2`). Лёгкие 1px-границы вместо плотных фонов карточек.
- **Тон копи**: минимализм, нижний регистр для меток-маркеров (`сегодня · 1/3`), серьёзный, не геймификационный. Никаких «Молодец! 🎉».

## Этический контракт продукта

Контент построен на принципах CBT-экспозиции, ACT и mindfulness-based attention training. См. методологические преамбулы в `CONTENT_*.md`. Особенно важно для будущих правок:

- **Цель задания — действие, а не реакция собеседника.** Контракт: «ты сделал свою часть, остальное — не ты».
- **Никаких pickup-паттернов** в «Общительности» (адресация по полу, ролевая игра, обман).
- **Никакого «преодоления любой ценой»**, никакой токсичной продуктивности, никаких 30-day challenges.
- **Срыв ≠ провал.** На уровне 3 «Дисциплины» — отдельный механизм «возвращения в тот же день», не «начать с понедельника».

При добавлении заданий проверяй: не нарушает ли формулировка эти рамки.

## Контент

75 заданий в `src/data/tasks.ts` (3 навыка × 5 уровней × 5 вариантов). Формат строгий — менять только синхронно с соответствующим `CONTENT_*.md`. Прежде чем редактировать задание, прочитай блок «Зачем это» в .md — там психологическое обоснование.

## Что НЕ входит в MVP

См. полный список в `MVP_REQUIREMENTS.md`. Главное:
- Социальные функции, аватар-кастомизация, AI-генерация заданий, геймификация (бейджи/лидерборды), iOS, платежи.
- Несколько активных навыков одновременно — заложено как post-MVP направление («аватар как RPG-персонаж»).

## Чего избегать

- **Не парсить `task.id` строками** для логики (например, для определения уровня) — использовать `getTaskById`.
- **Не вызывать `navigation.reset`** из табов для перехода на root-экраны без `getParent()`.
- **Не править babel/metro/expo версии руками** — только через `npx expo install <pkg>`.
- **Не добавлять реакции собеседника как метрику успеха** в задания «Общительности» — это противоречит этическому контракту.
- **Не использовать эмодзи в UI** без явного запроса. Иконки — только `lucide-react-native`.
- **Не добавлять `console.log` или dev-флаги** в продакшен-код. Удалять перед коммитом.
- **Не создавать новые `*.md` файлы документации** без явной просьбы пользователя.

## Дев-нюансы под мобилу и российский рынок

- **Push**: на устройствах без Google Services (часть Huawei и др. RU-сборок) FCM не приходит. Запланировано — RuStore Push SDK как fallback.
- **Supabase** хостится вне РФ: для MVP приемлемо, на пост-MVP — возможно self-host на Selectel/Timeweb.
- **Модерация текста рефлексии**: обязательна для прохождения ревью RuStore (анти-мат / анти-спам). Не реализовано.
- **AsyncStorage изолирован по устройству**: до lazy-registration данные на смене устройства теряются. Это сознательный trade-off для MVP.

## Известные технические долги

- Storage: `addCompletion` не атомарный (read-push-write). В однопользовательском UI безопасно, но при синхронизации с Supabase нужно переделать.
- `lastCompletedAt` хранится в аватаре, но нигде не читается (`pickTaskForToday` работает с журналом). Мёртвое поле — почистить при первом рефакторинге.
- Веб-бандл проходит, но `expo-haptics` на вебе молча no-op. Не баг, просто учитывать при тесте.

## Git и публикация

Репо: https://github.com/DanPtrh/gran. Две ветки — `main` и `develop`.

### Правило веток

**По умолчанию работаем в `develop`.** Любые фичи, эксперименты, незавершённые куски, экраны в полировке, любые коммиты в обычном рабочем цикле — всё идёт на `develop`. Не нужно спрашивать у пользователя «куда коммитить», ответ всегда `develop`.

**`main` — только релизные состояния.** Туда переезжаем только когда:
- Готовится сборка для подачи в RuStore / Google Play
- Пользователь явно сказал «делаем релиз» / «переводим в main»

Релизный мердж — обычным `git checkout main && git merge develop && git push origin main`, потом возврат на `develop` для продолжения работы. **Никаких force-push** на main без явного разрешения.

### Гигиена коммитов

- Чувствительные ключи (Supabase URL/anon-key, FCM, любые external API tokens) — через `.env` + `expo-constants`, никогда в коде. `.env*.local` уже в `.gitignore`.
- Перед коммитом — проверять `git status`, чтобы случайно не уйти `node_modules`, `.expo`, временные SVG из `/tmp`, отладочные `console.log`.
- Коммит-сообщения — содержательные, на русском или английском (соблюдай стиль предыдущих коммитов в репо). С `Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>` если коммит создавался ассистентом.

### Сборка для стора

Через **EAS Build** (`eas build --platform android`). AAB заливается в Google Play и RuStore раздельно. Перед сборкой убедись, что `__DEV__`-bypass-логика в `pickTaskForToday` действительно отключится (продакшен-флаг `__DEV__ === false` это сделает автоматически).
